# 손인사(안녕 wave) 개발 경과 — 보류 (2026-07-08)

FK 단일 본 제어로 "자연스러운 손인사"를 만들려다 **실패, 보류**. 재시도 시 반복 삽질을 막기 위해
시도·실패 원인·재개 방향을 기록한다. 코드는 삭제 않고 **주석으로 감춰둠**(아래 "코드 위치").

## 목표

- 동작: 오른손 들어 좌우로 흔드는 "안녕" 인사 (첨부 참고 이미지 = 상완 거의 내림 + 팔꿈치 접어
  하완만 세우고 손 좌우로).
- 트리거(결정됨): **① 등장(ready) 시 1회** + **② DebugPanel 수동 버튼**. idle 랜덤·게임이벤트는 제외.

## 검증된 오른팔 축 (이번에 얻은 소득)

| 채널 | 의미 | 비고 |
|------|------|------|
| `armR.z` | 프론탈 들기/내리기 | rest +1.3(내림). ↓일수록 옆으로/위로 벌어짐 |
| `armR.x` | 앞뒤 스윙 | **음수=앞** |
| `armR.y` | 상완 롤(길이축) | 내린 팔에선 잘 안 보이나, **팔꿈치 접힘'면'을 결정**. 든 팔에선 스윙 보임 |
| `elbowR.z` | 팔꿈치 굽힘 | 우+. 값↑ = 하완 더 접힘(≈2.4에서 손이 어깨, 3.5는 과굴곡) |

## 시도 이력

1. **armR.z 스윕** (0.08↔0.48) → 든 팔이 **위아래 flap**. 좌우 흔들기 아님. ✗
2. **상완 수평 들기(armR.z 0.3) + armR.y 오실레이션** → 팔 전체가 **덜렁덜렁**. 사용자: 상완이 아니라
   하완이 올라와야. ✗
3. **하완 주도(armR.z~1.0, elbowR.z 강한 굽힘) + armR.y 흔들기** → 상완이 흔들려 거슬림. 사용자:
   elbowR.z가 실제 흔드는 부위, 상완 흔들림 최소화 요구. ✗
4. **elbowR.z 오실레이션(2.9↔3.5)로 흔들기, armR.y 제거** → **하완이 상완과 겹침**(접힘면이 정면이라
   포개짐). 사용자: 하완은 반드시 상완 '앞'에. ✗
5. **armR.y 상수 롤로 접힘면 앞으로** → (a) **팔꿈치가 뒤로** 접힘(부호 반대) + (b) 접힘면이 앞이 되니
   elbowR.z 흔들기가 **앞뒤**가 됨. 좌우 흔들기를 armR.y로 재이관 시도했으나 수렴 실패 → **보류**. ✗

## 실패의 근본 원인

- **커플링 지옥**: `armR.y`(상완 롤)가 *하완 앞뒤 배치*와 *elbow 흔들기 방향*을 동시에 지배 →
  "하완을 상완 앞에" + "손 좌우 흔들기" + "상완 정지"를 **단일 본 3개(z/x/y)+elbow로 동시 만족 불가**.
  한 조건을 맞추면 다른 조건이 깨지는 순환.
- **손목(Hand 본) 미사용**: 사람의 손인사 좌우 흔들기는 실제로 **손목 flick**이 주도한다. 이번엔
  상완/팔꿈치만 건드려서 부자연 + 커플링에 갇힘.
- euler XYZ 합성으로 축이 서로 간섭(회전 순서 의존).

## 검증 방식 전환 (2026-08-04) — 재개의 전제

위 5회 실패의 진짜 원인은 축 지식 부족이 아니라 **검증 루프**였다. 값을 바꿀 때마다 사람이 눈으로
보고 "덜렁덜렁"·"겹침" 같은 표현으로 알려주는 구조라, 에이전트가 스스로 성패를 못 봤고 추측으로
값을 굴렸다. → **수치 프로브 도입**([probe.ts](../src/companion/anim/probe.ts), `npm run probe`).

위 실패 5건을 그대로 술어로 번역했다:

| 시도 | 육안 표현 | 수치 술어 | 기본 임계 |
|---|---|---|---|
| 1 | "위아래 flap" | 흔들림 주축 (span x vs y) | `horizontal` |
| 2·3 | "팔 전체 덜렁덜렁" | 상완 최대 각변화 | ≤0.15 rad |
| 4 | "하완이 상완과 겹침" | 손↔상완선분 최소거리 | ≥0.06 m |
| 5 | "팔꿈치가 뒤로 접힘" | `mean(hand.z − elbow.z)` | ≥0.02 m |
| 목표 | "손을 든다" | `mean(hand.y − shoulder.y)` | ≥0 |

**실측 기준선**(2026-08-04, male_sample): idle 차렷 = 이동폭 0.005·손높이 −0.46 / 오른손짓 제스처
= 이동폭 0.119·상완각 0.284·**주축이 앞뒤(z=0.151 > x=0.119)**. 임계값은 전부 초기 추정치라
wave 구현 중 재보정 대상(`WAVE_TARGETS`).

## 재개 방향 (다음에 시도할 것)

1. **★손목(Hand) 본으로 흔들기** — 상완·팔꿈치로 "하완 앞·세움" 자세만 **정적** 확정하고, 좌우
   흔들기는 `RightHand` 본 회전 오실레이션으로. 팔은 고정, 손만 까딱 → 커플링 회피 + 자연스러움.
   (채널 `handR.*` 신설 + `channels.ts` apply에 본 매핑 추가 필요)
2. **IK 도입** — 손 목표점 고정 후 팔 자세 풀이. 과하지만 정밀. [ik-plan.md](ik-plan.md).
3. **authored 클립** — Blender에서 수작업 키프레임 → import. 절차 애니와 별개 경로.
4. **눈높이 타협** — 좌우 흔들기 포기하고 "손 들어 잠깐 유지"(정적 raise + 살짝 tilt)로 단순화.

## 다음 세션 착수 지점 (2026-08-04 기준)

프로브(측정)는 **완료**됐고, wave 구현은 **미착수**다. 순서:

1. **`RightHand` 축 실측** — `channels.ts`에 임시로 `handR.x/y/z`를 뚫고 값을 하나씩 넣어
   `npm run probe -- --ms 2000` 으로 어느 축이 `swingAxis: horizontal`을 만드는지 확인.
   지난 실패는 축을 추측해서 났다 — 이번엔 측정으로 확정한다.
2. `handR.*` 채널 정식화 ([channels.ts](../src/companion/anim/channels.ts) `apply()` + `BASELINE`).
   현재 손가락 16본은 바인드돼 있으나 **손목(Hand) 본은 채널이 없다**.
3. `WAVE` 주석 해제 후 손목 주도로 재작성 → `npm run probe` PASS 까지 반복.
   상완은 정적 자세만 잡고(raise), 흔들기는 손목이 전담 → 커플링 회피.
4. 트리거 4곳 주석 해제 (위 "코드 위치").

## ⚠️ 임계값 조정 규율 (2026-08-04)

**프로브는 임계를 자동 조정하지 않는다.** `WAVE_TARGETS`([probe.ts](../src/companion/anim/probe.ts))는
박힌 상수이고 `evaluateArm`은 그것과 비교해 합불만 낸다. 적응·학습·자동보정 없음.
→ 바꾸려면 **사람이 손으로 고쳐야 하고**, 그래서 "PASS가 안 뜨니 기준을 낮춘다"는 경로가 실재한다.
(이 오해가 실제로 한 번 났다 — "프로브가 알아서 하겠지"가 오염의 전형적 입구다.)

조정 시 반드시 둘을 구분한다:

| | 근거 | 조치 |
|---|---|---|
| **정당** | 물리적으로 도달 불가능한 기준이었음 — 예: 손목 flick만 써도 FK 상속으로 상완이 구조적으로 0.2rad 움직임 → `maxArmSwing 0.15`는 애초에 만족 불가 | 상향 + **실측 근거를 이 문서에 기록** |
| **부당** | 0.28이 나왔는데 안 떨어지니 0.3으로 올림 | ❌ 프로브 무력화 |

차이는 **"물리적으로 불가능해서"냐 "통과시키고 싶어서"냐**다. 앞은 측정기의 오류를 고치는 것이고,
뒤는 측정기를 끄는 것이다. 실패 모드를 못 잡는 프로브는 없느니만 못하다.

**사용자가 임계 완화를 요구하더라도 자동으로 따르지 말고**, 어느 쪽 근거인지 구분해 제시한 뒤
판단을 받는다. 조정했으면 조정 사실과 근거를 반드시 보고한다 — 조용히 바꾸는 것이 최악이다.
