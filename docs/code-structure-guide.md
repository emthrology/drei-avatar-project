# 코드 구조 판단 가이드

프로젝트 구조가 "최적인지" 헷갈릴 때 쓰는 일반 기준. 미관이 아니라 **변경을 쉽고 안전하게** 하기 위한 것.

## 대전제

> 구조의 목적 = **다음 변경이 쉽고 국소적이게** 만드는 것.
> 구조가 변경을 어렵/위험하게 만들면 손보고, 아니면 그냥 둔다.

리팩토링 자체가 목적이면 "개발만 하면 됨"(개발 원칙2 위반). 항상 **이득**이 있어야 한다.

## 5가지 일반 기준

### 1. 응집도 (Cohesion) — 같이 변하는 건 같이 둔다
한 파일/모듈은 **한 가지 책임**. "이 파일은 왜 바뀌나?"의 답이 여러 개면 응집이 낮음.

### 2. 결합도 (Coupling) — 모듈 간 의존을 줄인다
A를 고치면 B·C·D까지 따라 고쳐야 하면 결합이 높음. 추상화(인터페이스/채널)로 세부를 감추면 결합이 낮아짐.

### 3. 관심사 분리 (Separation of Concerns) — 층을 나눈다
엔진/로직 · 데이터/콘텐츠 · UI · 설정이 한 파일에 섞이지 않게. 층마다 바뀌는 이유·속도가 다름.

### 4. 단일 출처 (DRY / Single Source of Truth)
같은 지식이 두 곳에 중복되면 안 됨. 한 곳을 고치고 다른 곳을 잊으면 버그.

### 5. 크기 / 발견성 (Size / Discoverability)
파일/함수가 너무 길면 쪼갠다. 이름·위치로 "어디 있는지" 찾을 수 있어야 함.
- 본 규칙: **동질 파일 3개 이상 → 폴더로 묶기** (2개까지는 flat 유지)

## 문제를 "냄새"로 감지 (체크리스트)

- [ ] 한 파일이 **여러 이유로** 바뀐다 → 응집 낮음
- [ ] 기능 하나 바꾸는데 **여러 파일**을 동시에 고친다 → 결합 높음
- [ ] **같은 코드/지식이 복붙**돼 있다 → DRY 위반
- [ ] 파일/함수가 **너무 길다**, 또는 **이름 붙이기 어렵다** → 책임 과다
- [ ] **순환 import**가 있다 → 경계가 잘못됨
- [ ] UI 파일이 **로직/전역 상태**를 들고 있다 → 관심사 미분리

## 판단 규칙 (헷갈릴 때)

> 이 구조가 **곧 할 변경**(예: 부위 교체, IK, 무드 톤)을 막거나 위험하게 만드나?
> - 그렇다 → 리팩토링 (실질 이득)
> - 아니다 → 그냥 둠 (YAGNI — 미리 과설계 금지)

## 적용 절차

1. **목적 정의** — 무엇을 위한 정리인가 (유지보수성 / 다가올 기능 / 특정 불편)
2. **진단** — 위 5기준·냄새로 각 파일/모듈을 `적합 / 분할후보 / 주의`로 라벨링
3. **ROI 우선순위** — 효과 큰 것부터. 안 아픈 건 안 건드림
4. **소단위 실행 + 검증** — 한 번에 크게 X. PR 단위로, 매 단계 `tsc`+`build`+`npm test`(순수 로직 단위 테스트)+수동 검증이 안전망. 동작 불변 = 비퇴행(원칙1)

## 흔한 오해

- "타입과 데이터를 같은 파일에 두면 안 된다" → **아님.** 타입은 그 데이터/로직과 가까이 두는 게 보통 좋음(응집). 타입을 빼는 건 **여러 모듈이 공유**하거나 파일이 너무 클 때만.
- "파일은 무조건 작게" → 아님. **하나의 책임이면** 길어도 됨. 문제는 길이가 아니라 **책임이 여러 개**인 것.
- "폴더가 깊을수록 정리됨" → 아님. 과한 중첩은 오히려 발견성↓. 3+ 규칙 정도가 실용적.
