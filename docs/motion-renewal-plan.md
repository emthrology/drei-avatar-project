# 절차 레이어 리뉴얼 계획 (VRMA 대비 부드러움 격차)

브랜치 `feat/motion-renewal`. 진단 2026-08-06.
선행 라운드: [motion-naturalness-plan.md](motion-naturalness-plan.md)(2026-07, overlap·smootherstep·micro-drift 완료).

## 결론 먼저

VRMA가 절차보다 부드러운 이유는 **본 커버리지가 아니라 스케줄러의 보간 결함이 1순위**다.
로드맵의 기존 가설(52본 중 9본만 구동)은 사실이지만 **2순위**이며, 그것만 고쳐도 격차가 안 닫힌다.

실측 대조 (절차=헤드리스 5분 idle/neutral · VRMA=글TF 트랙 직접 파싱):

| 지표                             | 절차 idle       | VRMA_03(가장 정적인 클립) |
| -------------------------------- | --------------- | ------------------------- |
| 구동 본                          | 7               | 51 / 52                   |
| 정지 비율 (<0.5°/s)              | 74~89%          | 6~31%                     |
| **본별 최장 정지**               | **3.3 ~ 14.5s** | **0.00 ~ 0.29s**          |
| 총 회전량 중 상위 5% 프레임 비중 | **65.5%**       | 31.6%                     |
| Spine 평균 각속도                | 2.38°/s         | 2.02°/s                   |

**진폭 부족이 아니다** — Spine 평균 속도는 오히려 절차가 더 크다. 총량이 아니라 **분포**가 문제다:
순간에 몰아 쓰고 나머지를 얼려 둔다.

## 증상 → 근본 원인

### 원인 ① 리드인 세그먼트가 보간이 아니라 1차 저역통과 필터 〔최우선〕

[scheduler.ts:267](../src/companion/anim/scheduler.ts#L267) `arr[j] ?? this.live[ch]` 가 `null` 시작값을
**매 프레임 다시** 읽는다. `live` 는 직전 프레임 출력([scheduler.ts:288](../src/companion/anim/scheduler.ts#L288))이라
보간이 `out = (1−α)·out_직전 + α·target` **재귀**가 된다. 주석의 의도("null = 시작값으로 **채움**")와
어긋나는 구현 미끄러짐이다.

`dt=1000ms` 단일 전환 실측 (`smooth:0.7`):

| 경과           | 의도한 값 | 실제 60fps | 실제 30fps | 실제 120fps |
| -------------- | --------- | ---------- | ---------- | ----------- |
| 30%            | 0.1311    | 0.5244     | 0.3360     | 0.7567      |
| 50%            | 0.5000    | 0.9952     | 0.9422     | 1.0000      |
| 99% 도달       | 1.000s    | **0.483s** | 0.567s     | 0.417s      |
| 피크 속도 시각 | 0.500s    | **0.300s** |            |             |

파급:

- **`smooth:0.7`(smootherstep) 투자가 사실상 무효화**됐다 — 화면에 나오는 곡선은 이징이 아니라 필터의 것.
  선행 라운드가 기대만큼 체감되지 않은 구조적 이유.
- 짧게 확 움직이고 남은 시간 정지 → 버스트 집중도 65.5%
- `head`·`pose`·`armPose` 루프는 dt 세그먼트가 **1개뿐**이라 100% 이 경로.
  (`breathing`·`blink` 은 3세그먼트라 첫 램프만 해당)
- **프레임레이트 종속** — DprGovernor 로 부하가 변하는 컴패니언에서 동작 속도가 달라진다.

### 원인 ② 본 커버리지 7 / 52 〔2순위, 로드맵 기존안〕

[channels.ts:185-196](../src/companion/anim/channels.ts#L185-L196) 이 잡는 본은 Head·Chest·Spine·UpperArm·LowerArm·Hand 뿐.
Neck·Shoulder·UpperChest·Hips·다리 전무. VRMA 는 51/52 본을 쓴다. 머리 회전이 단일 관절인 것이 특히 크다
(VRMA: head 11.18°/s + neck 5.74°/s 로 분절).

### 원인 ③ "램프 후 대기" 구조 자체 〔3순위, 설계 변경〕

①을 고쳐도 **최장 정지 14.5s 는 안 줄어든다**(패치본 실측 14.3s). 루프가 `delay 대기 → 단일 램프 → 대기`라
채널이 구조적으로 얼어붙는다. micro-drift([channels.ts:92-104](../src/companion/anim/channels.ts#L92-L104))는
최대 0.24°/s 로 **인지 문턱(0.5°/s)의 절반**이라 이걸 못 가린다.

### 원인 아님 — overlap 시차

VRMA 의 근위→원위 시차를 속도 상호상관으로 재보니 클립마다 −33ms ~ +1000ms 로 일관성이 없다.
**식별 불가 → 건드리지 않는다.** (현행 35ms 유지)

| **1**   | 리드인 보간 수정 | `scheduler.ts` (~3줄)                                        | `npm run motion:stat` + `npm run verify` | 버스트 5% ≤ 45% · 최대각속도 ≤ 120°/s |

### 0단계 — 측정 하네스 (먼저 만드는 이유)

이후 모든 단계를 **브라우저 없이 한 명령으로** 검증하기 위해서다.

진단에 쓴 일회용 스크립트를 그대로 옮겨오는 게 아니다 — 그건 하네스로 못 쓴다:
① `BASELINE`·`DRIFT` 를 [channels.ts](../src/companion/anim/channels.ts) 에서 **인라인 복사**해 들고 있어
채널이 늘면 사본만 조용히 낡는다 ② 실행기가 `sucrase-node`(= `tailwindcss` 의 전이 의존, 미선언)라
Tailwind 만 올려도 깨진다 ③ 단정문이 없어 회귀를 못 잡는다.
→ 상수는 export 해 단일 소스로, 실행기는 이미 선언된 vitest 로, 예산 단정문을 단다.

**구현됨 (2026-08-06)** — `npm run motion:stat` (약 0.7초, 브라우저 없음):

- [motionProfile.ts](../src/companion/anim/motionProfile.ts) — 순수 로직. 스케줄러를 헤드리스 N분(기본 5분)
  구동해 본별 `정지비율 / 평균·최대 각속도 / 최장 정지` + 전역 `버스트 집중도 / 구동 본 수` 산출.
- [motionProfile.test.ts](../src/companion/anim/motionProfile.test.ts) — 예산 단정문 + 표 출력. `npm test` 에 포함.
- **결정성**: 시드를 프로파일러가 **자기 안에서** 주입한다(mulberry32 로 `Math.random` 을 try/finally 로 교체).
  호출부가 `vi.spyOn` 을 안 해도 항상 같은 수치 → `npm run motion:stat` 을 그냥 돌려도 비교 가능.
- **사본 금지**: `channels.ts` 가 `CHEST_INHALE_SCALE`·`DRIFT`·`DRIFT_AMP` 와 `driftAt(ch,t)` 를 export 하고
  `apply()` 와 프로파일러가 **같은 함수**를 쓴다. 채널→본 그룹도 채널 이름 규약(`<본>.<축>`)에서 파생한다.
- **한계**: euler 채널 델타의 제곱합을 각속도 근사로 쓴다(쿼터니언 정확값 아님). 본 간 절대 비교가 아니라
  **같은 지표의 단계 간 변화**를 보는 용도. 얼굴 채널(blink/emo.\*)은 제외 — 표정은 멈춤이 결함이 아니다.
- **`worstStill`·`peakSpeed` 는 구동 본 기준** — idle 에서 아예 안 쓰는 손목(`handL/R`)은 뺀다.
  '안 쓰는 본'과 '쓰는데 얼어 있는 본'은 다른 문제다.

**기준선 (seed 1, 5분, idle/neutral)** — 이후 단계는 이 표와 비교한다:

| 지표                 | 기준선 | VRMA_03 |
| -------------------- | ------ | ------- |
| 버스트 집중도 상위5% | 63.3%  | 31.6%   |
| 최대 각속도          | 238°/s | 49°/s   |
| 최장 정지            | 16.35s | 0.29s   |
| 구동 본              | 7      | 51      |

예산 단정문은 **현 상태가 통과하는 값**으로 시작한다(특성화). 각 단계 완료 시 그 단계의 완료 기준까지 조인다.
⚠️ **통과시키려고 예산을 완화하지 않는다** ([[dont-weaken-verification]]). 완화가 필요하면 근거와 함께 보고.

덤으로 4단계의 근거를 테스트로 박아뒀다 — `DRIFT` 의 최대 각속도(진폭 × 각주파수)가 인지 문턱 미만임을
단정한다. drift 를 키우면 이 테스트가 깨지므로, 4단계에서 문턱을 넘길 때 의식적으로 갱신하게 된다.

### 1단계 — 리드인 보간 수정

`tick` 에서 세그먼트 진입 시 `null` 을 **1회만** 고정한다(`vs` 는 factory 가 인스턴스마다 새로 만드므로 mutate 안전):

```ts
const arr = clip.vs[ch];
if (arr[j] === null) arr[j] = this.live[ch] ?? this.baseline[ch] ?? 0;
```

- **기존 `scheduler.test.ts` 12 케이스 전부 통과 확인됨** — 특성화 테스트가 필터 거동을 핀으로 박아두지 않았다.
- 패치본 시뮬 실측: 버스트 5% 65.5→**39.8%** · 최대각속도(LowerArm) 245→**103°/s** · Head 정지 74.4→**48.8%** ·
  이징 곡선이 의도값과 일치하고 **프레임레이트 무관**해짐.
- ⚠️ **부작용: 모든 동작이 명목 duration 을 다 쓴다 → 지금보다 느리고 부드러워진다**(의도했던 값). 2단계에서 보정.
- ⚠️ **`WAVE` 의 첫 raise 세그먼트도 해당** → `npm run verify`(vitest + 양 캐릭터 wave 프로브) 필수.
  프로브 임계값은 **하나도 바꾸지 않는다**. 깨지면 값이 아니라 원인을 본다.

### 2단계 — 데이터 재튜닝

1단계로 전환이 실제 2배 길어지므로 `moods.ts` 의 `dt`/`delay` 만 조정한다. **`vs`(진폭)는 건드리지 않는다** —
진폭은 이미 VRMA 급이라는 게 진단 결과다. 3·4단계 전에 넣는 이유: 뒤 단계가 이 체감 위에 얹히므로.

### 3단계 — 본 커버리지 (apply 레이어 파생)

개별 클립 저작 금지. `channels.ts` `apply()` 에서 **기존 채널 값으로부터 새 본을 파생**시켜 `moods.ts` 무변경으로
전 동작에 소급한다. 우선순위: ①어깨 추종(`armL/R.z` 비례 Shoulder 회전) ②목 분배(`head.rotate*` → Head/Neck ≈0.65/0.35,
총 회전량 유지) ③UpperChest 분배 ④`DRIFT` 에 neck/shoulder 추가.
**계수 0 = 기존 출력 바이트 동일**로 두고 `useAnimator` 에서만 활성.

⚠️ **신규 본 = VRMA 레이어 회귀 위험** — 새 본을 채널이 소유하면 [useVrmaLayer.ts:228-231](../src/companion/anim/vrma/useVrmaLayer.ts#L228-L231)
의 「소유 판별」결과가 바뀐다(복귀 목표가 rest0 → live 로 전환). VRMA 손인사 복귀를 반드시 재검증.

### 4단계 — 연속 신호화 (게이트 있음)

`delay 대기 → 램프 → 대기`를 상시 진동(다주파수 합성)으로 바꾸거나, micro-drift 를 인지 문턱 위로 승격.
**설계 변경이라 착수 전 별도 판단** — 0~3단계 결과를 보고 아직 로봇 같은지부터 확인한다. 아니면 안 한다(원칙②).

## 비퇴행 전략

- 단계마다 1 PR, 앞 단계 완료 후 다음. 원복 단위 = 커밋.
- 새 파라미터는 **기본값 no-op**(off 시 기존 출력 바이트 동일) → 0단계 하네스로 고정.
- 1단계만 예외로 **출력이 의도적으로 바뀐다**(결함 수정). 그래서 0단계 하네스를 먼저 만들어 변화량을 수치로 남긴다.
- 매 단계 `npm test` + `npm run motion:stat`, 손·팔을 건드리는 1·3단계는 `npm run verify` 추가.
